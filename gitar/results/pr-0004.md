<kbd>🔴 High risk</kbd> · Adding --reset deletes Affinity indices and the room-reports data stream, which could irreversibly erase stored search and report data.

Adds an Elasticsearch foundation via `scripts/es_setup.py` (`make es-setup`) that creates the `affinity-embed` inference endpoint, the `talks`, `people`, `room-state` and `incidents` indices, and the `room-reports` data stream with a 2-day ILM policy, plus a one-off Job manifest and a script that copies `.env` secrets into `app-credentials`. Approved with suggestions: `scripts/push-secrets.sh` uses server-side apply, so re-running it with a key missing from `.env` can delete that key from `app-credentials`, which could remove `OPENAI_API_KEY` and break the es-setup Job. Patching only the keys that are set, or fixing the header comment and warning about removed keys, would address this.

`kubectl apply --server-side --field-manager=push-secrets` treats each apply as the full set of fields that manager owns. If a key was pushed in an earlier run and is missing from `.env` in a later run (for example a teammate whose `.env` has only the Dash0 values), Kubernetes deletes that key from `app-credentials`. `--force-conflicts` also hands ownership of hand-created keys with the same names to this manager, so those keys can be deleted the same way later. That contradicts the header comment saying other keys stay as they are. When `OPENAI_API_KEY` is lost this way, the es-setup Job fails at `secretKeyRef` and the app loses its embedding key. Fix: patch only the keys that are set, using `kubectl patch secret --type merge` with `stringData`, or create the Secret first if it is missing. Or, at the least, fix the comment and warn that skipped keys are removed.
