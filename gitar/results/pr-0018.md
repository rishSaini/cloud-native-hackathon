<kbd>🟡 Medium risk</kbd> · Room-report aggregation and scheduled state updates could misclassify capacity or accessibility signals, affecting talk placement and attendee decisions.

Adds a room-state engine that recomputes open/full, captions, very_loud and access_blocked from a 30-minute ES aggregation of room reports, with hysteresis and a per-minute sweep CronJob. Changes are requested: the `room-state` partial update has no `retry_on_conflict`, so concurrent writers from the report route, the sweep, and the controller can get 409s. That can turn a stored report into a 500 and abort the sweep run partway through the rooms.

Several writers partially update the same `room-state` doc: the report route on two app replicas, the `room-state-sweep` CronJob every minute, and Rishabh's controller writing `seats_*`/`controller_seen_at`. Elasticsearch's update API does a read-modify-write and returns a 409 `version_conflict_engine_exception` when another update lands in between, unless `retry_on_conflict` is set. In `report_room`, `recompute_state` runs after `record_report` has already stored the report. So a 409 there returns a 500 to the user even though the report counted, and a retry from the user then gets a 429. In the sweep, one conflict kills the whole run, and the rooms after it are not recomputed that minute. Fix: pass `retry_on_conflict` to `es.update`. Partial-doc updates are safe to reapply. You could also catch `ConflictError` in the route so the 202 for the stored report is still returned.
