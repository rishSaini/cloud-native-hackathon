Adds K11 staff incident tracking: captions and access-blocked incidents open per room and kind, with acknowledge and resolve endpoints and a staff login route. Changes are requested before merge: the staff token is passed in the login URL where it can leak into traces and logs, concurrent recomputes can open duplicate incidents for one room, the open-incidents gauge is per-process and goes stale, custom telemetry names miss the required `talkscout.` or `search.` prefix, and a non-ASCII token causes `compare_digest` to return a 500 instead of a 401.

<details>
<summary>⚠️ <b>Security:</b> Staff token goes in the login URL and leaks into traces and logs</summary>

<kbd>📄 <a href="https://github.com/rishSaini/cloud-native-hackathon/pull/31/files#diff-40706f38b703cef839b8e29b85c7eb580111a9f5dd93989b9010f18c7b812e49R32-R38">backend/app/incidents/routes.py:32-38</a></kbd>

`GET /api/staff/login?token=…` puts the shared STAFF_TOKEN in the query string. The app runs under `opentelemetry-instrument` with the FastAPI/ASGI instrumentation, which records the request target and query (`http.target`/`url.query`) on the server span. Its URL redaction only covers a few AWS/GCS signature parameters, not `token`, so every staff login sends the secret to the tracing backend. It also ends up in uvicorn and gateway access logs and in browser history. The cookie also stores the raw token, so whoever reads it gets the master credential, not a session that can be revoked. Fix: accept the token in a POST body (or the `X-Staff-Token` header) and store a signed or HMAC-derived value in the cookie instead of the token itself.

<summary>⚠️ <b>Bug:</b> Concurrent recomputes can open duplicate incidents for one room</summary>

<kbd>📄 <a href="https://github.com/rishSaini/cloud-native-hackathon/pull/31/files#diff-4ed82c65b6434505a25dc030a635b2387473cbec77ecae95afa337162d09ba4cR47-R55">backend/app/incidents/store.py:47-55</a></kbd> <kbd>📄 <a href="https://github.com/rishSaini/cloud-native-hackathon/pull/31/files#diff-c8af2d7f2593c8f9f941beef34a083d5d703eeaff10990e5412051436fa74ae6R164">backend/app/reports/state.py:164</a></kbd> <kbd>📄 <a href="https://github.com/rishSaini/cloud-native-hackathon/pull/31/files#diff-c8af2d7f2593c8f9f941beef34a083d5d703eeaff10990e5412051436fa74ae6R177-R185">backend/app/reports/state.py:177-185</a></kbd>

`open_incident` searches for an active incident and only then indexes a new one under a random `inc-<uuid>` id. Two app replicas run (deployment `replicas: 2`), and the per-minute sweep CronJob runs `recompute` too. So two reports, or a report and the sweep, can both see the room's previous state with captions not `down`, both find no active incident, and both open one. Staff then see two incidents for the same room and kind, which breaks the one-per-room-and-kind promise. Fix: give the active incident a deterministic id, such as `f"{room}-{kind}-active"`, and index it with `op_type="create"`, treating a 409 as "already open". On resolve, re-key or delete that id.

<summary>⚠️ <b>Bug:</b> affinity_incidents_open gauge is per-process and goes stale</summary>

<kbd>📄 <a href="https://github.com/rishSaini/cloud-native-hackathon/pull/31/files#diff-4ed82c65b6434505a25dc030a635b2387473cbec77ecae95afa337162d09ba4cR15-R29">backend/app/incidents/store.py:15-29</a></kbd>

The gauge reports a module-level `_open_count` that changes only when this process opens or moves an incident. It starts at 0 after every restart. Each of the two replicas exports its own number. Incidents opened by the sweep CronJob (`recompute` → `open_incident`) only change the short-lived CronJob process's copy. So the gauge often shows 0 or a stale number while incidents are open, and a sum across replicas double-counts. Fix: have the observable gauge callback query ES itself (`refresh_gauge(get_es())`, caching the result for a few seconds and returning the last value if ES errors), or export the count from one place only.

</details>
