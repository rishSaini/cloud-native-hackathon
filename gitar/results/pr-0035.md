<kbd>🟡 Medium risk</kbd> · The new seating solver changes group and table assignments; constraint-handling errors could seat blocked pairs together or fail to meet attendees’ needs.

Adds a pure-Python group solver (`app.solver.solve`) that seats people in 2-4 person groups under table seat, cap, and blocked-pair constraints, using greedy seeding followed by local search. Approved with suggestions: the `group.size` span attribute records the group count instead of a group size, the greedy phase is O(n³) and does not check `time_limit_ms` inside its loop, and `_hardness` ignores blocks made against a person, so the documented 'most blocks' ordering is not fully honored.

<details>
<summary>💡 <b>Bug:</b> <code>group.size</code> span attribute records the group count, not a group size</summary>

<kbd>📄 <a href="https://github.com/rishSaini/cloud-native-hackathon/pull/35/files#diff-33f0b28defcfc10a0dd602c9b21372fa188d7f495be905e4ae4065dcf23233b1R260">backend/app/solver/__init__.py:260</a></kbd>

`set_attrs(span, ..., group_size=len(groups))` sets `group.size` to the number of groups. The metric with the same name, `affinity_group_size`, records member counts per group ("Sizes of groups formed"). A solve that produces 12 groups of 4 puts `group.size=12` on the span, which misleads anyone comparing traces with the histogram. Set it to a real size, such as the largest or the mean group size, or leave the attribute off the span and rely on the histogram.

<summary>💡 <b>Performance:</b> Greedy phase is O(n³) and ignores <code>time_limit_ms</code></summary>

<kbd>📄 <a href="https://github.com/rishSaini/cloud-native-hackathon/pull/35/files#diff-33f0b28defcfc10a0dd602c9b21372fa188d7f495be905e4ae4065dcf23233b1R157-R171">backend/app/solver/__init__.py:157-171</a></kbd>

Each time `_greedy` adds a person, it builds a candidate list over all of `order`. It then calls `max` with a key that runs `order.index(q)`, an O(n) list scan, once per candidate. That is O(n) work per candidate, n candidates per add and up to n adds, so the phase is O(n³). The deadline is only checked in `_local_search`, so a large solve can run well past `time_limit_ms` before local search even starts. Precompute `rank = {p: i for i, p in enumerate(order)}` and use `-rank[q]`, and check the deadline inside the greedy loop.

<summary>💡 <b>Edge Case:</b> Hardness ignores blocks made against a person</summary>

<kbd>📄 <a href="https://github.com/rishSaini/cloud-native-hackathon/pull/35/files#diff-33f0b28defcfc10a0dd602c9b21372fa188d7f495be905e4ae4065dcf23233b1R152-R154">backend/app/solver/__init__.py:152-154</a></kbd>

`_hardness` counts only `len(st.p[person].blocked)`. The constraint itself goes both ways: `blocked()` checks `a in b.blocked` as well as `b in a.blocked`. So someone blocked by many others but who blocked nobody is sorted as easy and placed late, even though they are among the hardest to seat. That is not the documented order ("most blocks"). Precompute how many blocks involve each person in either direction and sort by that.

<details>
<summary>Count blocks in both directions (cache this if n is large)</summary>

````
def _hardness(st: _State, person: str):
    blocks = sum(1 for o in st.p if o != person and st.blocked(person, o))
    return (st.options[person], -blocks, person)
````
