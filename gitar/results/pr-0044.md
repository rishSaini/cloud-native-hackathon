<summary>✅ <b>Bug:</b> A failed Pod delete rolls back move counts for Pods already deleted</summary>

> <kbd>📄 backend/app/controller/reroute.py:45-59</kbd>
> `reconcile_reroutes` runs the whole loop in one `pool().connection()` transaction. The pool isn't autocommit, so the `moves` increments only commit when the block exits normally. Each Pod's `delete_namespaced_pod` call goes out to Kubernetes right away. If a later delete raises (for example a 404 because the NoExecute eviction or placement removed the Pod between the list and the delete, or any API error), psycopg_pool rolls back the transaction. That undoes the `count + 1` for every person whose Pod this pass already deleted. On the next lost capability in the same slot they get moved again, which breaks the once-per-slot rule. Fix: commit each person's increment before deleting (`with conn.transaction():` per Pod, or `conn.commit()`), and ignore a 404 from the delete.
