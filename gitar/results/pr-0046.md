<kbd>🔴 High risk</kbd> · Creating reciprocal group-based card grants changes who may view attendee profiles; mistaken group assignments could expose personal card details to unintended viewers.

Adds break groups: RSVP and group-formation logic, a solver-driven reconciler that creates table-affined Pods, and group APIs for the frontend. Changes requested before merge: the four new API routes have no tests in backend/tests/, and a failed group formation can leave Pods that no longer match the DB, which can seat people at the wrong table.

- Add route tests for `POST /api/breaks/{id}/rsvp`, `POST /api/staff/breaks/{id}/form`, `GET /api/groups/current` and `POST /api/groups/{id}/check-in`, covering the staff-token 401, 404s, card-grant filtering and check-in status mapping.
- Make group formation idempotent: commit DB rows before creating Pods, or verify the existing Pod's group label on 409, and run each break in its own transaction.
- Store the `running-late` check-in status instead of collapsing it to `on-the-way` or NULL.
- Rename the new spans and metrics (`solver.run`, `k8s.node.taint`, `affinity_*`) with the required `talkscout.` or `search.` prefix.

<summary>⚠️ <b>Bug:</b> A failed group formation leaves Pods that no longer match the DB</summary>

<kbd>📄 <a href="https://github.com/rishSaini/cloud-native-hackathon/pull/46/files#diff-ab11e911849b954bbac19ea3bdafe839ad445a1b2ad418198ea1a119b64b5e08R98-R112">backend/app/controller/groups.py:98-112</a></kbd>

`form_groups` creates member Pods inside the DB transaction that `reconcile_groups` holds open. Suppose any later `create_namespaced_pod` fails with a non-409 error, such as a quota 403 or a transient 5xx. The exception rolls back every `groups`, `group_members`, `card_grants` and `notifications` row, and also the work for any other break due in the same pass. The Pods already created stay. On the next pass `solve` runs again. If RSVPs or similarity changed in the meantime, it can produce different groups. Then the 409 handler keeps the old Pod (same name `attendee-{id}-{break}`), which still has the old `affinity.dev/group` label and node affinity to the old table. Kubernetes then seats the person at a different table from the one stored in the DB and shown by `/api/groups/current`. Two ways to fix it: commit the DB rows first and create Pods afterwards, so creation is idempotent against the stored groups, or on a 409 compare the existing Pod's group label and recreate it if it differs. Also run each break in its own transaction.

`check_in` accepts `here`, `on-the-way` and `running-late`, but it only stores a timestamp. Anything other than `here` becomes NULL. `current_group` then reports `myStatus` as None, and shows every other member who is not here as `on-the-way`. So someone who says they are running late appears as on-the-way to their group, and their own status reads as unset. The endpoint still echoes `running-late` back, which hides the problem.
