Changes are requested before merge: share links fall back to a public hardcoded signing key and ignore `card_grants.expires_at`, simultaneous mutual proposals can both return `pending` without creating a connection, unknown `displayId` values in `/api/connections` return a 500 and reveal which attendees exist, and the new API routes lack route tests.

<summary>⚠️ <b>Security:</b> Share links fall back to a public signing key, and DB expiry is ignored</summary>

<kbd>📄 <a href="https://github.com/rishSaini/cloud-native-hackathon/pull/52/files#diff-55d785474e176f37948be22f49e0edfe832f746b593ac9a599acd8c93b2ed6c3R23-R27">backend/app/cards/share.py:23-27</a></kbd> <kbd>📄 <a href="https://github.com/rishSaini/cloud-native-hackathon/pull/52/files#diff-55d785474e176f37948be22f49e0edfe832f746b593ac9a599acd8c93b2ed6c3R66-R70">backend/app/cards/share.py:66-70</a></kbd>

`_key()` quietly uses the hardcoded `affinity-dev-share-key` when `SHARE_SIGNING_KEY` is unset. Unlike `crypto.py`, it doesn't even log a warning. The repo is public, so anyone can sign tokens with that key. `view_shared_card` only checks the expiry inside the token and never reads `card_grants.expires_at`. If the secret is missing from the cluster, anyone who once held a QR link (and so knows the grant UUID) can re-sign it with a far-future expiry and view the card indefinitely, unless the grant is revoked. Fix: also select `expires_at` and reject when `now() > expires_at`. Fail at startup, or at least log a warning, when the key is unset outside local dev.

<summary>⚠️ <b>Bug:</b> Simultaneous mutual proposals can both return pending with no connection</summary>

<kbd>📄 <a href="https://github.com/rishSaini/cloud-native-hackathon/pull/52/files#diff-a308cf0d5e3cf13afebcccd97dc5eaae00e17ef415e7866a9e00ea55dfbc2927R45-R58">backend/app/social/routes.py:45-58</a></kbd>

Each request inserts its own proposal and then looks for the other person's proposal in the same uncommitted transaction. Under READ COMMITTED, if A and B propose at the same time (for example, both scan each other's QR), neither sees the other's uncommitted row. Both commit and get `pending`, and no `connections` row is written until someone proposes again. Fix: serialize on the pair, e.g. `SELECT pg_advisory_xact_lock(hashtext(a||':'||b))` inside `conn.transaction()` before the insert and select. Or use SERIALIZABLE and retry.

</details>
