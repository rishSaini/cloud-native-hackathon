**Cluster budget check** (`deploy/` changed)

The new `migrate` initContainer has requests and limits set. Init containers run before the app container, so a pod's effective request is the larger of the two. The app container is larger, so the pod needs no extra quota.

| Resource | Total (after this PR) | Budget | Status |
|---|---|---|---|
| CPU requests | 950m (app 2×100m, controller 100m, Elasticsearch 500m, Postgres 100m, room-state-sweep 50m) | 2 CPU | OK |
| Memory requests | 3008Mi (~2.94Gi) | 4Gi | OK |
| CPU limits | 3700m | 4 CPU | OK |
| Memory limits | 4352Mi (~4.25Gi) | 8Gi | OK |
| PVCs | 2 (Elasticsearch 5Gi, Postgres 1Gi) | 4 | OK |
| Storage | 6Gi | 20Gi | OK |

Every container, including the new init container, has requests and limits. Nothing is over budget.

During a rolling update, surge pods may briefly raise usage above these steady-state numbers.

**Pod/Node spec writes in this change**

The only change to a Pod spec is the new `migrate` initContainer in `deploy/deployment.yaml`. It adds:
- Container name: `migrate`
- Command: `python -m app.db.migrate --best-effort`
- Env `DATABASE_URL`, read from Secret `db-app`, key `uri` (a secret reference, not a value)
- Resources and securityContext

It adds no labels, annotations or Pod names. The existing `app: app` label is unchanged. No Node specs are touched.

The frontend and `migrate.py` changes build no Pods or Nodes. The new `saveErrorMessage` text only appears in the user's own browser. It holds no card text and is not written to any Pod or Node.

Nothing here carries card text, names, capability meanings or raw scheduler messages.
